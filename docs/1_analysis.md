# Інженерний опис аналогів

1. Wanderlog
    - **Архітектурний патерн:** Система базується на гібридній сервіс-орієнтованій архітектурі (SOA) з елементами монолітного ядра для обробки бізнес-логіки планування. Для підтримки спільного редагування маршрутів у реальному часі реалізовано подієво-керований підхід (Event-Driven) на рівні сесій. Масштабованість обмежена необхідністю підтримки тривалих stateful-з'єднань для колаборативних сесій.
    - **Протоколи передачі даних:** Взаємодія клієнт-сервер реалізується через REST API для транзакційних операцій (CRUD) та WebSockets (або Server-Sent Events) для двосторонньої синхронізації стану редагування маршруту в реальному часі.
    - **Базовий стек даних:** Основне сховище — реляційна СУБД (PostgreSQL), доповнена NoSQL рішеннями (подібними до Firebase/Firestore) для обробки колаборативних даних. Кешування та управління сесіями забезпечується In-Memory СУБД (Redis). Консистентність даних у реальному часі досягається механізмами Operational Transformation (OT) або CRDT (Conflict-free Replicated Data Type).
    - **Критичні інженерні недоліки (Technical Bottlenecks):** Високе споживання оперативної пам'яті (RAM) на бекенді через необхідність утримання відкритих WebSocket-з'єднань для кожного активного користувача. Спостерігається збільшення затримки (Latency) при виконанні складних геопросторових запитів, оскільки система покладається на класичні індекси замість оптимізованого векторного пошуку для визначення релевантності локацій.
2.  Booking.com
    - **Архітектурний патерн:** Високонавантажена розподілена мікросервісна архітектура. Система історично еволюціонувала з масивного Perl-моноліту до тисяч ізольованих мікросервісів (переважно на Java). Масштабування відбувається горизонтально, проте супроводжується значним оверхедом на інфраструктурну оркестрацію (Kubernetes) та Service Mesh.
    - **Протоколи передачі даних:** Зовнішня маршрутизація та інтеграція з партнерами здійснюється через HTTP/REST та GraphQL. Внутрішня міжсервісна взаємодія оптимізована за допомогою gRPC (використання Protobuf для бінарної серіалізації) та асинхронних черг повідомлень (Kafka, RabbitMQ) для публікації подій бронювання.
    - **Базовий стек даних:** Шардовані та репліковані кластери MySQL/PostgreSQL для транзакційних даних, Cassandra для високоінтенсивного запису (логіювання, події). Забезпечення консистентності спирається на модель Eventual Consistency (узгодженість у кінцевому рахунку) для пошукових індексів, тоді як ядро бронювання вимагає строгих ACID-транзакцій з використанням двофазних комітів (2PC) або патерну Saga.
    - **Критичні інженерні недоліки (Technical Bottlenecks):** Проблема стану гонитви (Race conditions) під час пікових навантажень (Flash sales), що інколи призводить до овербукінгу через компроміси CAP-теореми (надання переваги Availability над Consistency у певних вузлах). Надзвичайна складність розподіленого трейсингу та висока вартість підтримки інфраструктури консистентності даних між тисячами баз даних.
3. Tripadvisor
    - **Архітектурний патерн:** Розподілена архітектура з акцентом на інтенсивне читання (Read-Heavy). Використовується патерн CQRS (Command Query Responsibility Segregation) для розділення потоків генерації відгуків (запис) та агрегації рейтингів/пошуку (читання).
    - **Протоколи передачі даних:** Широке застосування GraphQL Federation для агрегації даних із десятків різних доменних сервісів (авіа, готелі, ресторани) в єдиний граф. Класичний REST API для застарілих (legacy) модулів.
    - **Базовий стек даних:** PostgreSQL як джерело істини, масивні кластери Elasticsearch для повнотекстового пошуку та гео-запитів, Hadoop/Spark для офлайн-обробки аналітики (MapReduce). Кешування реалізовано через Memcached та Redis.
    - **Критичні інженерні недоліки (Technical Bottlenecks):** Складні проблеми з інвалідацією кешу (Cache Invalidation), що призводить до проблеми "застарілих даних" (Stale Data), коли користувачі бачать неактуальні ціни або статуси. Відсутність нативної підтримки векторного пошуку (Embeddings) у базовій архітектурі змушує систему покладатися на інвертовані індекси (BM25), що знижує семантичну точність при обробці складних природномовних запитів користувачів на планування поїздок.

### Аналітичний висновок підрозділу 1.2

Результати порівняльного аналізу засвідчують, що архітектурні рішення розглянутих аналогів мають обмеження, зумовлені їхнім функціональним призначенням. У Wanderlog гібридна SOA з монолітним ядром та необхідність утримання stateful-з'єднань WebSocket для кожної колаборативної сесії спричиняють високе споживання оперативної пам'яті та ускладнюють горизонтальне масштабування. Мікросервісна архітектура Booking.com, що спирається на Eventual Consistency для пошукових індексів, зумовлює ризик Race conditions за пікових навантажень, складність розподіленого трейсингу та високу вартість підтримки інфраструктури консистентності даних. Tripadvisor демонструє типові для Read-Heavy систем проблеми Cache Invalidation та Stale Data, а залежність від інвертованих індексів (BM25) обмежує семантичну точність обробки природномовних запитів. Жоден із розглянутих аналогів не містить вбудованого механізму комбінаторної оптимізації маршрутів, тому побудова розкладу подорожі залишається за користувачем.

Обраний у межах кваліфікаційної роботи технологічний стек спрямований на усунення зазначених обмежень. Архітектура SOA забезпечує розділення доменних сервісів без операційного оверхеду, характерного для керування сотнями або тисячами мікросервісів. Асинхронна обробка на основі Celery та RabbitMQ виносить ресурсомісткі операції (виконання CP-SAT solver, звернення до LLM) за межі циклу обробки HTTP-запиту, що усуває потребу в довготривалих stateful-з'єднаннях. Механізми acknowledgements у RabbitMQ та повторних спроб (retry) у Celery забезпечують відмовостійкість обробки задач. Застосування PostgreSQL із розширенням pgvector дозволяє зберігати реляційні та векторні дані в єдиному сховищі з ACID-гарантіями, що виключає необхідність окремого кластера Elasticsearch та синхронізації кешів. Використання Google OR-Tools (CP-SAT) забезпечує детерміноване знаходження допустимих розкладів за заданою множиною обмежень, чого не реалізовано в жодному з аналогів.

Водночас прийняті рішення передбачають архітектурні компроміси (trade-offs). SOA поступається мікросервісам у гранулярності масштабування окремих компонентів. Розширення pgvector є менш продуктивним за спеціалізовані векторні СУБД на великих обсягах даних. Асинхронна модель обробки вводить затримку між надсиланням запиту та отриманням результату, що потребує відстеження статусів задач. За очікуваних навантажень платформи зазначені обмеження вважаються прийнятними з огляду на спрощення експлуатації та підтримки. Деталізація проєктних рішень щодо структури сервісів, взаємодії черг повідомлень та схеми бази даних наведена в Розділі 2.
