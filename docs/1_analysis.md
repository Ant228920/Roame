## 1.5. Постановка задачі та формування вимог

### 1.5.1. Концептуальна модель To-Be

Цільова модель передбачає заміну розірваного ручного процесу наскрізним конвеєром обробки, в якому стохастичні та детерміновані обчислення ізольовано на архітектурному рівні:

1. **Прийом наміру.** Клієнт (`React SPA`) надсилає природномовний запит до `API Gateway` (`FastAPI`). Запит автентифікується (`JWT`) та перетворюється сервісом `Intent Parser` у структурований об'єкт `TripRequest` (дати, бюджет, категорії, темп). Відповідь `LLM` валідується за `JSON`-схемою (`Pydantic`); невалідна відповідь відхиляється до потрапляння в бізнес-логіку.
2. **Семантичний відбір кандидатів.** Опис наміру перетворюється на вектор (`Gemini Embeddings`); у `PostgreSQL` виконується `ANN`-пошук за `HNSW`-індексом `pgvector` з одночасним `SQL`-фільтром за географічним радіусом, категорією та графіком роботи. Результат — обмежена множина з 20–50 кандидатів, що зменшує розмірність задачі оптимізації.
3. **Асинхронна оптимізація.** API повертає клієнту `202 Accepted` з ідентифікатором задачі; задача публікується в брокер `Redis` і обробляється `Celery worker`-процесом у виділеній черзі `optimization`. `Worker` отримує матрицю транзиту (`Mapbox Matrix API` з кешуванням у `Redis`) та формує модель `CP-SAT`: жорсткі обмеження — часові вікна, тривалості візитів, транзит, бюджет; цільова функція — максимізація сумарної релевантності за мінімізації часу переїзду. Розв'язувач запускається з лімітом часу; у разі недосяжності повертається перелік конфліктних обмежень замість невалідного плану.
4. **Транзакційне резервування.** Мандрівник підтверджує маршрут; `Booking Service` резервує слоти ресурсів у межах транзакцій `PostgreSQL` із блокуванням рядків та `exclusion`-обмеженнями на інтервалах часу. Складений маршрут обробляється за патерном `Saga`: у разі відмови будь-якого кроку виконуються компенсуючі транзакції для вже зарезервованих слотів.
5. **Подієві сповіщення.** Зміни стану бронювань і маршруту публікуються як події; `Notification Service` (`aiogram`) доставляє їх у `Telegram` без участі основного потоку обробки запитів.
6. **Верифікація зворотного зв'язку.** Відгук приймається лише для бронювання зі статусом `COMPLETED`, підтвердженим персоналом (`Proof-of-Visit`), що підвищує достовірність даних для подальшого ранжування.

#### Таблиця 1.2 — Відповідність вузьких місць As-Is та інженерних рішень To-Be

| Вузьке місце (As-Is) | Рішення (To-Be) |
| :--- | :--- |
| $O(n^2)$ ручних запитів транзиту | Пакетний запит `Mapbox Matrix API` + кеш у `Redis` |
| $O(n!)$ ручний вибір порядку | `CP-SAT` розв'язувач з лімітом часу |
| Логістичні галюцинації `LLM` | `LLM` лише формує кандидатів; розклад будує детермінований розв'язувач |
| Синхронне блокування на 10–40 с | Асинхронна черга `Celery`, відповідь `202 Accepted`, опитування статусу |
| Відсутність атомарності складеного бронювання | Патерн `Saga` з компенсуючими транзакціями |
| `Overbooking` за конкурентного доступу | `SELECT ... FOR UPDATE` + `exclusion constraint` на `tstzrange` |
| Неверифіковані відгуки | `Proof-of-Visit`: відгук лише після статусу `COMPLETED` |

### 1.5.2. Функціональні вимоги (Core Features)

- **Модуль автентифікації та контролю доступу (`Auth Service`):**
  - **`FR-1.`** Реєстрація та автентифікація користувачів з видачею пари `JWT` (`access` / `refresh`) та розмежуванням прав за ролями `traveler`, `owner`, `staff` (`RBAC`) на рівні кожної кінцевої точки (`endpoint`) та кожного об'єкта.
- **Модуль інтерпретації наміру та семантичного пошуку (`Recommendation Service`):**
  - **`FR-2.`** Перетворення природномовного запиту у структурований об'єкт `TripRequest` засобами `Gemini API` з валідацією відповіді за `JSON`-схемою.
  - **`FR-3.`** Генерація векторних вбудовувань (`embeddings`) для закладів і запитів та відбір `top-N` кандидатів через `ANN`-пошук `pgvector` (`HNSW`) з комбінованими `SQL`-фільтрами (радіус, категорія, графік роботи).
- **Модуль оптимізації (`Optimization Worker`):**
  - **`FR-4.`** Побудова розкладу на 1–7 днів шляхом розв'язання задачі `VRPTW/TOPTW` засобами `Google OR-Tools CP-SAT` у фоновій задачі `Celery` з поверненням статусу задачі (`PENDING`, `RUNNING`, `SUCCESS`, `INFEASIBLE`, `FAILED`) та переліку конфліктних обмежень у разі недосяжності.
- **Модуль геосервісів (`Geo Service`):**
  - **`FR-5.`** Геокодування адрес, отримання матриць транзитного часу через `Mapbox API` з кешуванням у `Redis` та візуалізація оптимізованого маршруту на карті (`React` + `Mapbox GL JS`).
- **Модуль управління ресурсами та бронювань (`Booking Service`):**
  - **`FR-6.`** Управління власником закладу ресурсами та часовими слотами; атомарне резервування слотів для всіх точок маршруту з компенсуючими транзакціями (`Saga`) у разі часткової відмови.
  - **`FR-7.`** Прийом відгуків виключно для бронювань зі статусом `COMPLETED`, підтвердженим персоналом закладу (`Proof-of-Visit`).
- **Модуль сповіщень (`Notification Service`):**
  - **`FR-8.`** Доставка сповіщень у `Telegram` (`aiogram`) про зміну статусів бронювань, нагадування за 60 хв до візиту та оновлення маршруту за подіями з брокера повідомлень.

### 1.5.3. Нефункціональні вимоги (NFRs)

Класифікацію виконано відповідно до характеристик якості `ISO/IEC 25010`. Значення встановлено для конфігурації демонстраційного стенду (`Docker Compose`, `4 vCPU / 8 GB RAM`) і верифікуються навантажувальним тестуванням (`Locust` / `k6`).

#### Таблиця 1.3 — Матриця нефункціональних вимог (NFRs)

| `NFR-2` | Продуктивність | Семантичний `ANN`-пошук (`pgvector HNSW`, 100 000 векторів розмірності 768, `top-50`) на `p95 <= 150 мс`; повнота (`recall@50`) `>= 0,95` відносно точного пошуку | Скрипт `benchmark`, `EXPLAIN ANALYZE` |

| `NFR-16` | Супровідність | `CI`-конвеєр `GitHub Actions`: `ruff`, `mypy` (`strict` для доменних модулів), `pytest`; покриття тестами доменних модулів (оптимізатор, бронювання) `>= 80 %`, загальне `>= 70 %`; документація API — `OpenAPI 3.1` | `GitHub Actions`, `Codecov` |

### 1.5.4. Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка `Cloud-Native` вебплатформи сервіс-орієнтованої архітектури з асинхронною чергою обчислювальних задач для вирішення задачі автоматизованої побудови математично валідних розкладів подорожей та атомарного резервування просторово-розподілених ресурсів. Передбачено ізоляцію стохастичного компонента (інтерпретація наміру та семантичний відбір кандидатів засобами `Gemini API` і `pgvector`) від детермінованого розв'язувача задачі `VRPTW/TOPTW` (`Google OR-Tools CP-SAT`), що виконується у фонових `worker`-процесах `Celery` з брокером `Redis`. Для досягнення мети необхідно реалізувати функціональні вимоги `FR-1`–`FR-8` та забезпечити виконання нефункціональних вимог `NFR-1`–`NFR-16`, зокрема час відгуку API на `p95 <= 200 мс` при `300 RPS`, розв'язання задачі на 25 точок за `<= 10 с` та відсутність подвійних бронювань за конкурентного доступу.
